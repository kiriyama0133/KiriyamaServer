# 2026-09-16 工作日志（KiriyamaServer / kiriyamalauncher）

## 中继 HTTP 请求 10054「远程主机强迫关闭」问题诊断 + 客户端加固

### 现象（客户端日志）
- `16:22:55.257` ZeroTier 事件：已通过虚拟网卡加入网络，虚拟 IP 10.99.33.213。
- `16:22:59.259` `ListRoomsAsync`（GET /api/rooms）失败：HttpRequestException ← IOException ← SocketException 10054，耗时 4003ms。
- 调用栈在 `HttpConnection.InitialFillAsync`：**TCP 已建立、请求已发出，等响应首字节时被远端 RST**——不是客户端超时（超时是 8s 且报 TaskCanceled）。

### 结论
请求正好发生在 ZeroTier 入网后的隧道收敛窗口。最可能原因（按概率）：
1. 隧道刚打通时 UDP 通路抖动，在途 TCP 会话被掐；
2. 服务端进程那一刻重启/崩溃（联调期高频）；
3. 服务端防火墙/杀软对 ZeroTier 网卡（公用网络配置文件）的重置。

### 客户端加固（已实施，编译 0 错误）
- `HttpRelayServerClient`：
  - 新增 `ClientName = "RelayServer"` 专用命名客户端（DI 里 `AddHttpClient(ClientName)` + `SocketsHttpHandler`）。
  - 新增 `GetWithRetryAsync`：**GET 类接口**（ListGames/ListRooms×2/ListPlayers）遇瞬时网络错误自动重试，最多 3 次尝试、间隔 1s；`IsTransientNetworkError` = HttpRequestException 内层是 IOException/SocketException；HttpClient 超时（TaskCanceled 且用户未取消）也重试。**POST 一律不重试**（创建/加入房间、鉴权，避免重复提交）。
- `Data/DependencyInjection.cs`：命名客户端 primary handler 配置 `PooledConnectionLifetime=30s`、`PooledConnectionIdleTimeout=15s`——服务器重启/通路重建后不再复用已死连接。

### 服务端待排查清单（用户侧确认）
- 当时 `logs/logs.txt` 是否收到该请求 / 服务端是否重启。
- 监听地址：launchSettings 的 applicationUrl 是 `http://localhost:5000`（仅本机回环）；要被其它机器访问必须监听 `0.0.0.0`（`--urls` / ASPNETCORE_URLS / Kestrel 配置）。
- 服务端防火墙对 ZeroTier 网卡的入站放行（公用网络配置文件）。
- ZeroTier 网络 Flow Rules 是否有 reject/drop 影响客户端→服务端 HTTP 端口。

### 关键教训
- 判断 10054 类问题先看调用栈位置：`ConnectAsync` 阶段 = 连不上（监听/防火墙）；`InitialFillAsync`/读响应阶段 = 连上了但被中途掐（进程重启、隧道抖动、安全软件）。

## 服务端监听地址修复（10054 根因定位）

### 根因
服务端日志明确显示 `Now listening on: http://localhost:5000`（仅回环），且 `Hosting environment: Production`（生产环境不走 launchSettings.json）。Kestrel 默认只绑 localhost，Linux 部署后客户端走 ZeroTier 虚拟 IP（10.99.x.x）访问根本进不来 → 连接被重置（10054）。

### 修复
- `src/WebApi/Program.cs`：`builder.WebHost.ConfigureKestrel` 显式 `options.ListenAnyIP(port)`，端口从 `Kestrel:Port` 配置读、默认 5000。覆盖回环 + 局域网 + ZeroTier 虚拟网卡。
- `src/WebApi/appsettings.json`：加 `"Kestrel": { "Port": 5000 }`。
- 编译 0 错误（仅既有 SA1629 警告）。

### 部署提醒
- 客户端填的中继服务器地址用服务器 ZeroTier 虚拟 IP（10.99.38.37）或局域网 IP，端口 5000。
- 服务器防火墙（ufw/firewalld/云安全组）放行 5000/tcp，并确认 ZeroTier 网卡不受限。
- 服务端仍保留 `UseHttpsRedirection`（http 请求不受影响，因为未配置 HTTPS 端口时该中间件不重定向）。

## 房间内出现两个相同用户（重复成员）修复 + 成员行去掉头像

### 根因
- 服务端 `GameRoom.Join` 完全不按 NodeId 去重：每次 join 都新增一条 Player 记录（新 Guid、同昵称）。
- 触发场景：上次退出房间的 leave 请求丢失（10054/断开局域网/关窗未上报）、或 join 响应失败后用户重试 join → 同一节点在服务端留存两条记录。
- 客户端房间页按 PlayerId 匹配，两条记录 PlayerId 不同 → 显示两行一模一样的用户。
- 且旧 `LeaveRoom` 用例只删 `FirstOrDefault`，退出一次还剩一条。

### 修复
- 服务端 `GameRoom`：`Join` 改为按节点幂等（先 `RemoveByNodeId` 再加入，重进自己的旧记录会腾出名额，不受满员限制）；新增 `LeaveByNodeId`（`RemoveAll`）替代按单条 Guid 的 `Leave`。
- 服务端 `LeaveRoom` 用例：改用 `LeaveByNodeId` 一次清光该节点全部遗留记录；`ClearRoomTagAsync` 改传 `input.NodeId`。
- 客户端 `RoomPageViewModel`：`RoomPlayerRow` 增加 `NodeId`；`ApplyPlayers` 匹配顺序 `FindPlayer(PlayerId) ?? FindByNodeId(NodeId)`，同一节点的遗留多条记录合并为一行（兜底）。
- 客户端 `RoomPageView.axaml`：成员卡片删掉 `AccountCircle` 头像图标，行内容 = 昵称 + 「虚拟 IP：x.x.x.x」，右侧保留延迟（用户明确：不要头像，只要昵称 + 虚拟 IP）。
- 两端编译 0 错误。

### 教训
- 同一文件的多个 Edit 不能放在同一批并行调用——会基于旧快照互相覆盖（本轮连续两次踩坑：LeaveRoom.cs 的 `input.NodeId` 修复、RoomPageViewModel 的 FindByNodeId 方法都被并行编辑回退，靠编译错误才发现）。同文件编辑必须串行。
- 服务端幂等性要在领域层兜底（join 幂等 / leave 全量清除），不能指望客户端不重试。
